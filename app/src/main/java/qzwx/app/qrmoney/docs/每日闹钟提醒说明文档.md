# QRMoney 用餐提醒闹钟模块说明文档

> 模块功能：每天中午 12:00 提醒「该吃午饭了」、下午 17:00 提醒「该吃晚饭了」，到点以系统通知形式弹出；用户点击通知后直接打开 App 主页。
>
> 适用环境：Android 16（API 36）及以上，同时兼容 Android 12–15。不使用 `setRepeating()`，改用 `setExactAndAllowWhileIdle()` 单次设置 + 触发后重设，以保证在 Doze 模式下准时。
>
> 文档版本：v1.0　最后更新：2026-10-12

---

## 一、快速结论（先看这段）

1. **不需要常驻后台**。闹钟时间保存在系统服务 `AlarmManagerService` 里，不在 App 进程里；App 被划掉或系统回收后，到点仍会响（原生 Android 行为）。
2. **手机重启后闹钟会丢失**，因此必须靠 `BootReceiver` 在开机时重建——这是本模块能长期工作的前提。
3. **国产 ROM（小米 / 华为 / OPPO / vivo）默认会拦截被杀 App 的闹钟广播**，表现为「设置成功但不响、也不报错」，需要引导用户把 App 加入自启动白名单与省电无限制。
4. **通知栏点了没反应**是最常见的二次问题，原因是没调用 `setContentIntent()`；同时必须同时处理 `onCreate`（冷启动）与 `onNewIntent`（热启动）两个入口。
5. **改通知内容改 `NotificationHelper`；改提醒时间改 `MealReminderScheduler`；改触发后的动作改 `MealAlarmReceiver`；改权限与组件注册改 `AndroidManifest.xml`；改点击后的页面跳转改 `MainActivity`**。这五句话覆盖了 90% 的定制需求。

## 三、各文件详细说明

### 3.1 `MealReminderScheduler.kt` —— 闹钟调度核心

**职责**：把「每天 12:00 和 17:00」翻译成两个具体的毫秒时间戳，交给系统 `AlarmManager`。

关键实现点：

- 使用 `Calendar.HOUR_OF_DAY` 设 12 与 17，并把秒、毫秒归零，保证准点。
- 若计算出的时间已过去（例如用户 13:00 才打开 App），则自动 `add(Calendar.DAY_OF_MONTH, 1)` 推到明天，避免立即误触发。
- 用 `setExactAndAllowWhileIdle()` 而非 `setExact()`：前者能穿透 Doze 休眠模式，后者在息屏一段时间后会被系统推迟。
- 两个闹钟使用不同的 `requestCode`（`REQUEST_CODE_LUNCH = 1001`、`REQUEST_CODE_DINNER = 1002`），使它们成为相互独立的闹钟，取消其中一个不影响另一个。
- `PendingIntent` 使用 `FLAG_UPDATE_CURRENT or FLAG_IMMUTABLE`：Android 12+ 强制要求显式声明可变性，且 `UPDATE_CURRENT` 保证重复设置时新参数生效。

**常见定制**：

| 需求 | 改哪里 |
|---|---|
| 改提醒时间（如加早餐 8:00） | 在 `scheduleToday()` 里增加一组 `calendar.set(HOUR_OF_DAY, 8)` + `setExactAlarm(...)` |
| 改成每 2 小时提醒一次 | 改为 `for` 循环按小时间隔批量设置 |
| 只在工作日提醒 | 在设置前判断 `calendar.get(DAY_OF_WEEK)` 是否在周一到周五 |
| 支持用户自定义时间 | 从 `SharedPreferences` 或 Room 读取小时/分钟，替换写死的 12 与 17 |
| 用户关闭提醒 | 调用 `alarmManager.cancel(pendingIntent)`，requestCode 要与设置时一致 |

### 3.2 `MealAlarmReceiver.kt` —— 闹钟触发入口

**职责**：系统到点后回调 `onReceive()`，这里是整条链路中**最容易漏写一行代码**的地方。

必须做两件事：

1. 根据 `intent.action` 区分午餐 / 晚餐，调用 `NotificationHelper.showNotification()`。
2. **调用 `MealReminderScheduler(context).scheduleToday()` 重设下一次**。

第 2 点是单次闹钟机制的生命线。`setExactAndAllowWhileIdle()` 只响一次，响完即作废，不在 `onReceive` 里重设，结果就是「今天响了明天不响」。

**注意**：`onReceive()` 运行在主线程，且有约 10 秒的执行时间限制。当前逻辑只做「发通知 + 设闹钟」，耗时极短，安全。若未来要在此处加网络请求或数据库写操作，必须改为 `goAsync()` 或转交给 `WorkManager` / 协程。

### 3.3 `BootReceiver.kt` —— 开机重建

**职责**：手机重启后，系统会清空所有已设闹钟（这是 Android 的设计，不是 bug）。监听 `BOOT_COMPLETED` 广播后重新调用 `scheduleToday()`。

**必须同时满足三个条件才能生效**：

1. `AndroidManifest.xml` 中声明 `RECEIVE_BOOT_COMPLETED` 权限。
2. `<intent-filter>` 里注册 `android.intent.action.BOOT_COMPLETED`（部分厂商 ROM 还需要 `QUICKBOOT_POWERON`）。
3. 用户**至少打开过一次 App**——Android 3.1 起，未启动过的 App 处于「停止状态」，系统不会向其发送任何广播。

第 3 点是大量「开机后不响」的真正原因，且无法用代码绕过，只能引导用户打开一次 App。

### 3.4 `NotificationHelper.kt` —— 通知样式与点击行为

**这是定制频率最高的文件**，通知长什么样、点完去哪，全在这里。

**渠道（NotificationChannel）**：Android 8+ 要求通知必须先归属到一个渠道。渠道一旦由系统创建，**再次修改属性（如震动、重要性）不会生效**——这是最经典的坑。改了渠道属性却看不到效果时，要么卸载重装，要么换个新的 `CHANNEL_ID`（例如 `meal_reminder_channel_v2`）。

**通知重要性**：`IMPORTANCE_HIGH` 才会弹横幅 + 响铃 + 震动；`IMPORTANCE_DEFAULT` 只会在通知栏静默出现，`LOW` / `MIN` 则完全无声。

**点击跳转**：通过 `setContentIntent()` 绑定一个 `PendingIntent.getActivity(...)`，指向 `MainActivity`。配合 `Intent.FLAG_ACTIVITY_CLEAR_TOP or FLAG_ACTIVITY_SINGLE_TOP`，避免重复创建 Activity。

**由于本模块只要求「打开主页」，而主页本身就是 `MainActivity` 的 `setContent { QApp() }`，因此 `MainActivity` 里的 `handleNotificationIntent()` 可以留空**——通知点进来，`MainActivity` 启动即渲染主页，无需额外跳转。这也是为什么当前 `TODO` 没有内容却依然能正常打开 App。

### 3.5 `MainActivity.kt` —— 启动入口与权限检查

**职责**：App 启动时完成「权限检查 + 闹钟设置 + 通知点击处理」三件事。

关键细节：**必须同时处理 `onCreate` 与 `onNewIntent` 两个入口**。

- App 未运行时点通知 → 走 `onCreate`
- App 已在后台时点通知 → `MainActivity` 走 `singleTop` 不会重建，只走 `onNewIntent`

漏掉 `onNewIntent` 的典型症状：「第一次点通知能打开，之后怎么点都没反应」。

**权限检查顺序建议**：先通知权限（`POST_NOTIFICATIONS`，Android 13+ 运行时申请），再精确闹钟权限（`SCHEDULE_EXACT_ALARM`，Android 12+ 需跳转系统设置页手动开启）。后者**没有系统弹窗**，用户可以选择拒绝，因此代码里不要假设「跳转设置后一定已授权」，应在 `onResume()` 里再次校验，或监听 `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` 广播。

### 3.6 `AndroidManifest.xml` —— 权限与组件注册

本模块新增 3 条权限、2 个 Receiver：

```xml
<!-- 精确闹钟权限（Android 12+，默认拒绝，需用户手动开启） -->
<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM" />
<!-- 开机广播权限 -->
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
<!-- 通知权限（Android 13+，运行时申请） -->
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
```

```xml
<!-- 闹钟 Receiver：不带 intent-filter，exported 可设为 false -->
<receiver
    android:name="qzwx.app.qrmoney.receiver.MealAlarmReceiver"
    android:exported="false" />

<!-- 开机 Receiver：带 intent-filter，exported 必须为 true -->
<receiver
    android:name="qzwx.app.qrmoney.receiver.BootReceiver"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
        <action android:name="android.intent.action.QUICKBOOT_POWERON" />
    </intent-filter>
</receiver>
```

**顺带提醒**：项目中已有的 `BillChangeReceiver` 声明为 `exported="true"`，且监听的是自定义广播 `ACTION_BILL_CHANGED`。由于 `exported=true` 意味着任意 App 都能向它发广播，若该 Receiver 内有账单修改类逻辑，存在被恶意 App 伪造广播触发的风险，建议改为 `exported="false"`（内部通信无需对外暴露）；而 `QReceiver_BillHistogram` 是桌面小组件，需要 Launcher 发送 `APPWIDGET_UPDATE`，必须保持 `true`。

### 3.7 `QZWXApplication.kt` —— 提前建渠道（建议）

把通知渠道的创建从 `NotificationHelper.showNotification()` 移到 `Application.onCreate()`，可以避免「第一次发通知时渠道尚未就绪导致通知被系统静默丢弃」。改动很小，收益明显，建议补上。

## 五、部署与验证步骤

### 5.1 代码合入

按第三节的清单把 5 个新建文件放入对应包路径，注意 `package` 声明必须与目录一致（例如 `receiver/` 目录下的文件顶部应为 `package qzwx.app.qrmoney.receiver`）。`MainActivity.kt` 与 `AndroidManifest.xml` 按 3.5、3.6 节内容修改。

**常见错误**：`AndroidManifest.xml` 中 `android:name` 写的是全限定类名，如果文件实际在 `receiver` 子包下而 Manifest 里漏写 `.receiver`，会直接编译报错。可用 Android Studio 在 `android:name` 处按 `Ctrl + Space` 让 IDE 自动补全，100% 确认类路径。

### 5.2 权限自检验收（Android 16）

安装后首次打开，依次确认：

1. 系统弹窗申请「通知」权限 → 允许。
2. 自动跳转「闹钟和提醒」设置页 → 允许。
3. 若跳过了第 2 步，需在系统设置 → 应用 → QRMoney → 权限 → 闹钟和提醒 中手动开启。

### 5.3 功能验证

**第一步：10 秒快速测试**

在 `MainActivity` 的 `setContent` 里临时放一个测试按钮（正式版务必换回 `QApp()`）：

```kotlin
setContent {
    QAppTheme {
        Button(onClick = {
            MealReminderScheduler(this@MainActivity).setExactAlarm(
                MealReminderScheduler.REQUEST_CODE_LUNCH,
                MealReminderScheduler.ACTION_LUNCH,
                System.currentTimeMillis() + 10_000
            )
        }) { Text("测试提醒(10秒后)") }
    }
}
```

**第二步：杀进程测试（关键）**

1. 点测试按钮，确认 10 秒后通知弹出、点击能打开主页。
2. 再次点测试按钮设置闹钟。
3. **划掉最近任务，彻底杀死 App**。
4. 等待 10 秒，观察是否仍会弹出通知。

这一步能直接判断当前 ROM 是否会拦截后台广播。

**第三步：开机测试**

1. 设置好闹钟。
2. 重启手机。
3. 开机后不打开 App → 到点**不应**响（App 处于停止状态，系统不发送 `BOOT_COMPLETED`）。
4. 打开一次 App → 到点应正常响。

## 六、已知限制与风险

### 6.1 国产 ROM 后台广播拦截

这是本模块在实际设备上**最大的不确定性来源**，且与代码质量无关。

| 品牌 | 默认行为 | 用户需手动操作 |
|---|---|---|
| 小米 / MIUI / HyperOS | 杀进程后拦截广播 | 自启动管理 → 允许；省电策略 → 无限制 |
| 华为 / EMUI / HarmonyOS | 杀进程后拦截广播 | 应用启动管理 → 手动管理 → 三项全开 |
| OPPO / ColorOS | 杀进程后拦截广播 | 电池 → 该 App → 允许后台运行 |
| vivo / Funtouch / OriginOS | 杀进程后拦截广播 | 电池 → 后台高耗电 → 允许 |
| 三星 | 部分拦截 | 电池 → 未监控的应用 → 加入 |
| 原生 Android / Pixel | 正常 | 无需操作 |

**应对建议**：在检测到闹钟未按时触发时，弹 Dialog 引导用户跳转自启动设置页。各大品牌入口不同，需按品牌硬编码跳转 Intent。

### 6.2 精确闹钟权限可被用户随时关闭

用户在系统设置中关闭「闹钟和提醒」权限后，所有已设闹钟**立即全部失效**，且不会收到任何回调。建议在 `onResume()` 中重新检查该权限，失效时提示用户重新开启。

### 6.3 渠道修改不生效

通知渠道是「一次写入」的：创建后修改其重要性、声音、震动，系统会直接忽略。务必通过更换 `CHANNEL_ID` 或卸载重装来使修改生效。

### 6.4 `onReceive` 主线程 10 秒限制

当前逻辑安全。若未来在 `MealAlarmReceiver.onReceive()` 中加入网络请求、数据库批量写入等操作，必须使用 `goAsync()` 或转交 `WorkManager`，否则会触发 `BroadcastReceiver` 超时，导致该次广播被系统终止。

### 6.5 `singleTop` 与 `onNewIntent`

`MainActivity` 使用 `singleTop` 启动模式。若后续在通知点击后需要跳转到非首页的具体页面，除了在 `handleNotificationIntent()` 中处理，还需注意：通过 `NavBackStack` 做页面跳转时，要确保跳转发生在 `QApp()` 的 Composition 完成之后，否则可能拿不到 `pagerState` 或 backStack 实例。建议用一个 `MutableState<Boolean>` 或 `Channel` 把事件从 `MainActivity` 传递给 `QApp()`，在 `LaunchedEffect` 中消费。

## 七、故障排查流程

```
通知完全没出现
 ├─ 1. Logcat 查 canScheduleExactAlarms()
 │    ├─ false → 精确闹钟权限未开，跳转设置页
 │    └─ true  → 继续
 ├─ 2. Logcat 查 MealAlarmReceiver.onReceive 是否被调用
 │    ├─ 未调用 → 闹钟未设置成功 / 被 ROM 拦截
 │    │    ├─ 检查 PendingIntent 是否带唯一 extra（防系统复用）
 │    │    └─ 做「杀进程测试」判断是否为 ROM 拦截
 │    └─ 已调用 → 继续
 ├─ 3. 检查通知权限（POST_NOTIFICATIONS）
 ├─ 4. 检查通知渠道是否已创建、IMPORTANCE 是否为 HIGH
 │    └─ 渠道改了属性？换 CHANNEL_ID 或卸载重装
 └─ 5. 检查电池优化是否把 App 设为「受限」

通知出现但点击没反应
 ├─ 1. 是否调用了 setContentIntent()
 ├─ 2. PendingIntent 的 requestCode 是否为 0（与已有冲突）
 └─ 3. 是否同时处理了 onCreate 与 onNewIntent 两个入口

只响一次，第二天不响
 └─ MealAlarmReceiver.onReceive() 末尾是否调用了 scheduler.scheduleToday()

重启后不响
 ├─ 1. 是否声明 RECEIVE_BOOT_COMPLETED 权限
 ├─ 2. 是否注册 BOOT_COMPLETED 的 intent-filter
 └─ 3. 用户是否至少打开过一次 App（未启动过的 App 收不到开机广播）
```

---

## 八、后续扩展建议

1. **用户可配置**：在设置页提供时间选择器 + 开关，把小时/分钟与开关状态存入 `SharedPreferences`，`MealReminderScheduler` 读取后设置。
2. **WorkManager 双保险**：对提醒可靠性要求极高时，可同时用 `WorkManager` 的 `OneTimeWorkRequest` 设 12:00 / 17:00 的延迟任务。`AlarmManager` 与 `WorkManager` 走的是不同唤醒路径，一个被 ROM 拦截时另一个可能仍能触发。
3. **前台 Service 保活**：若双保险仍不满足，可把调度逻辑移入前台 Service（`START_STICKY`），代价是通知栏会常驻一条「服务运行中」提示。
4. **通知点击跳转记账页**：利用当前已预留的 `from_notification` / `reminder_type` 这两个 Extra，在 `handleNotificationIntent()` 中通过事件机制通知 `QApp()` 切换到对应 Tab 并弹出记账录入。
5. **提醒历史与防打扰**：记录上次提醒时间，避免重复提醒；提供「免打扰时段」设置。
